# 0004. Конфигурация компилируется, расширения — WASM

- **Статус:** Принято
- **Дата:** 2026-09-21

## Контекст

Цель — максимально гибкая, полностью настраиваемая система. Первая мысль —
описывать всё в JSON и интерпретировать. На горячем пути 1M eps это неверно
дважды: по производительности и по устройству.

## Решение

1. Конфигурация разбирается один раз и **компилируется в план исполнения**.
   Интерпретации конфига на событие нет нигде.
2. Логика выражается **декларативными DSL** (Sigma для детектов, выражения —
   CEL или VRL), а не флагами конфига.
3. Произвольная логика пользователя — **WASM-плагины**, а не форк репозитория.
4. Поверхностный формат конфига — **TOML/YAML**, валидация — **JSON Schema**.

## Почему не «всё в JSON»

### Стоимость на горячем пути

Разбор и обход дерева конфига на каждое событие при 1M eps — это миллионы
аллокаций и промахов кэша в секунду. Правильный порядок: разобрать → провалидировать
→ **скомпилировать в неизменяемый план** (индекс предикатов, битовые маски,
таблицы переходов) → атомарно подменить план по версии. Горячий путь читает
только скомпилированный артефакт.

### Inner platform effect

Бесконечно настраиваемая система превращается в плохой язык программирования:
условия, циклы и переменные в YAML. Правило границы:

- **Конфиг выражает «что»** — какие источники, какие поля, какие пороги, какая
  ретенция.
- **DSL выражает «как ищем»** — Sigma-правило, CEL-выражение.
- **Плагин выражает «как обрабатываем»** — произвольный код в песочнице.

Флаг, добавляемый в конфиг, обязан отвечать на вопрос «какое значение здесь
осмысленно у двух разных пользователей». Иначе это код.

### JSON неудобен людям

Нет комментариев, нет висящих запятых, болезненные многострочные значения.
Поверхностный формат — TOML для плоского конфига, YAML для вложенного, со
строгой схемой. JSON Schema при этом остаётся каноном валидации независимо от
поверхностного формата: одна схема даёт и проверку, и автодополнение в IDE, и
генерацию документации.

## Расширяемость через WASM

Пользователю нужны свои парсеры, свои обогатители и свои действия в плейбуках.
Варианты: форк (неприемлемо), встроенный скриптовый язык (медленно, небезопасно),
динамические библиотеки (небезопасно, ломают ABI).

Берём WASM через Wasmtime:

- песочница по умолчанию, отказ ресурсам по умолчанию;
- скорость, близкая к нативной;
- плагин пишется на любом языке, компилирующемся в WASM;
- лимиты по памяти и по времени исполнения на вызов;
- прецеденты: Envoy, data transforms в Redpanda.

Границы плагинов: парсер источника, обогатитель, действие плейбука, экспортёр
алертов. Движок матчинга остаётся нативным.

## Конфиг под генерацию LLM

Настройка через ИИ работает не от того, что формат JSON, а от того, что схема
строгая и ошибки внятные. Требования к каждому конфигурируемому объекту:

- JSON Schema с описаниями полей и перечислимыми значениями;
- валидация до применения, с указанием пути к полю и допустимых вариантов;
- не менее трёх примеров рядом со схемой;
- `--dry-run`, показывающий скомпилированный план без применения.

Схема, удовлетворяющая этому, одинаково хорошо заполняется человеком, IDE и
языковой моделью. Отдельного «AI-режима» конфигурации не делаем.

## Последствия

- Изменение конфига требует перекомпиляции плана — закладываем атомарную
  горячую подмену с версионированием и откатом.
- Появляется граница ABI плагинов, которую нужно версионировать с первого релиза.
- Часть гибкости сознательно недоступна через конфиг и требует плагина. Это
  осознанный отказ от «настраиваемости всего».

## Когда пересмотреть

Накладные расходы вызова WASM окажутся значимыми на per-event пути (замер:
более 5% времени обработки) → выносить такие точки в нативные интерфейсы.
